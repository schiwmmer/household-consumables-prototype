## 1. 产品概述

**一句话定义**：一个面向双职工带娃家庭的微信原生小程序，让"每一件耗材还剩多少、该不该现在下单"在两步之内闭环。

**核心心智**：
1. **不是记账本** — 不记你上一次买了多少钱、不记批次、不记历史价格。
2. **是先知** — 提前 3 天告诉你"产妇垫还剩 1 包，要不要趁今晚下单"。
3. **是定位器** — "东西在哪"的答案不再是问配偶而是翻小程序。
4. **是采购前的决策辅助** — 不买不用急，买时心有数。

**目标用户**：一线及新一线城市双职工家庭，**家务采购决策者 + 执行者** 同为一人的场景（即"采购责任人"专注单独维护清单）。

**目标用户典型画像**：
- 年龄 28-40 岁，每日通勤 > 1 小时
- 配偶同样高工时，家庭靠老人帮带或托育
- 1-2 个婴幼儿或 2-3 个学龄儿童
- 热衷电商促销，价格敏感度中等偏高（价差 > 50 元时会主动等促销）
- 家中储物空间大但不规整（柜子多、层数多、搬动后难找）

## 2. 用户场景全景图

> **查缺补漏锚点**：以下 8 个场景基于访谈 + 产品外脑推演，其中 ★ = PRD v1 原覆盖，⭐ = v2 新增。

### 场景 S1 ★ 补货前夜犹豫（核心场景）
**时间**：22:00-23:00（下班、孩子睡着后的唯一时间槽）
**触发**：打开淘宝想买某化妆品但纠结"家里还有没有"
**期望**：打开小程序扫一眼，确认剩余天数 < 3 后立刻下单
**关键指标**：首页"剩余 N 天"读取耗时 < 1 秒

### 场景 S2 ★ 电商促销来时备货决策
**触发**：双11/黑五前 1 天，或收到"你收藏的 XX 正在打折"
**期望**：一键导出"哪些商品未来 7 天内会跌破安全库存"，决策是否跟活动买
**关键指标**：采购清单生成 ≤ 3 次点击

### 场景 S3 ⭐ 突击检查"孩子用品还能撑多久"
**触发**：老人打电话说"尿不湿快没了"，但你手上没有具体数字
**期望**：在电话里打开小程序 → 报出"婴儿 NB 还剩 2 包约 7 天"，让老人心里有底
**关键指标**：紧急场景下 5 秒内读到核心数据

### 场景 S4 ⭐ 配偶/老人找不到东西
**触发**：对方问"纸巾放哪了"
**期望**：小程序直接显示"客厅/白色柜第二层"，不再有"好像在卧室？"
**MVP 边界**：仍需要采购维护者手动维护；不做 V2 的夫妻协同编辑，但在首页故意把位置信息做成**大字、高对比、免登陆可读**（方便给家庭成员截图发微信）

### 场景 S5 ⭐ 生日/节日应急采购
**触发**：妈妈说明天要用某品牌面霜送人，让你买
**期望**：快速找到"在哪买"的链接 + 判断"需不需要补货"
**MVP 边界**：不做外链，仅预留"上次购买链接"字段，由用户手动粘贴

### 场景 S6 ⭐ 疫苗接种/入园/旅行前的物资筹办
**触发**：带 2 岁孩子回老家 3 天，不确定带几包尿布够
**期望**：按人数 + 天数估算总包数
**MVP 边界**：人数动态模版覆盖该场景（模板"母婴待产包"已有 12 项基础品）

### 场景 S7 ⭐ 照护老人场景
**触发**：帮异地父母管理纸尿裤/护理垫，电话问"还够不够"
**期望**：打开小程序一眼可见"老人护理"品类全部余量
**MVP 边界**：老人本人不是核心用户，由子女代理；不做老人版大字体（小字体截图解决）

### 场景 S8 ⭐ 双职工错峰维护
**触发**：老公上晚班顺手补充了大米，老婆不知道；次日老婆又买一袋
**MVP 边界**：不做成实时同步；但在首页刻意保留"最近修改时间戳"让配偶抬头可见，减少重复采购

## 3. MVP 范围

### IN（MVP 必做，v2.0 原型已完整覆盖）
- [x] 手动录入（分类、品牌、品名、规格、数量、位置、预计天数）
- [x] 扫码录入（条码匹配 → 未命中兜底手动）
- [ ] 估算法消耗倒计时（前端冷启动算）
- [x] 余量状态三色可视化（绿/黄/红）
- [x] 微信订阅消息推送到货前提醒（原型阶段 toast 替代）
- [x] 本地存储（原型用 SQLite 路径）
- [x] **批量模版导入（v2.0 新增）** — 4 个预制模版 × 动态人数 × 12 项示例
- [x] **4 条入库路径（v2.0 新增）** — 拍照 / 语音 / 扫码 / 手动
- [ ] 家庭人数动态修改（已在原型中实现步进器）；**真正的 V2 迁移点**
- [x] **存储位置可编辑下拉 + 一条"编辑列表"跳转入口**

### OUT（明确不做，列 V2+）
- 云端多人协同（含夫妻错峰共用一个账号）
- 价格监控/活动降价提醒
- 购物小票 OCR 批量录入
- 智能称重硬件
- 后台定时推送（依赖小程序冷启动或订阅消息）
- **批次历史**（single active row）
- 智能推荐比价

- ❌ 不做"谁负责买"的角色分派

## 5. 用户旅程地图（端到端，MVP 上线后第一周）

### Journey A：首次进入，无数据
```
[微信入口] → [授权页面] → [空态首页：4 个入口卡片 + 模版推荐]
    → 用户倾向：试模版导入（12 项母婴待产包 1 键录入 → 门槛最低）
    → [批量调整页] → 调整人数 + 确认导入
    → 首页出现 12 个带色点卡片 → 成就感建立 → 形成"以后就读这"心智
```
**首周 KPI**：首次导入完成率 > 70%

### Journey B：每日巡检
```
[首页] → 扫一眼上方"即将用完 5 件" + 胶囊 tab（母婴 / 日用 / 急救）
    → 点击红点卡片进详情
    → 拖动条调整剩余 / 直接标记用完
    → 退出（全程 < 30 秒）
```
**首周 KPI**：每日 DAU 巡检平均时长 < 45 秒

### Journey C：补货时刻
```
[首页单点红色警示] → 点进商品详情 → [点"一键采购清单" / 复制商品名]
    → 跳转电商 App（非小程序内）下单 → 回来改剩余数量
```
**首周 KPI**：详情→电商→回来 完成率 > 60%（Mean：在复制 + 跳转）

### Journey D：电话应急
```
[老人来电话] → [单手操作小程序] → 首页 → 关键字搜索
    → 3 秒内读出"NB 2 包 7 天" → 回复老人
```

## 6. 数据模型（v2.0 微调）

### 与 v1 相同的保留点
- `items`：商品主数据
- `categories`：分类（7 项默认 + 用户可增）
- `spec_templates`：规格模板（按分类预置）
- `item_specs`：商品-规格值
- `inventory`：单 active 行，无批次
- `alerts`：提醒记录

### v2.0 新增/修改的表

#### family_members（家庭人数快照 — v2.0 新增）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | |
| role | TEXT | elder / adult / child |
| count | INTEGER | 数量 (>=0) |
| updated_at | TEXT ISO | 最近修改时间 |

**设计决策**：单独成表而非 inventory 字段，因为**人数是全局属性**，影响所有商品的推荐数，单独维护便于：
1. 一处修改、全局联动
2. 未来 V2 支持按人设推不同商品（如老人护理 vs 儿童尿布）

#### storage_locations（收纳位置字典 — v2.0 新增）
| 字段 | 类型 | 说明 |
|------|------|------|
| loc_id | INTEGER PK | |
| path | TEXT | `客厅/白色柜子顶部`（"/"分隔房间+位置） |
| is_builtin | INTEGER | 1=预置 / 0=用户自建 |
| sort_order | INTEGER | 在 <select> 中出现顺序 |

**设计决策**：
- 不存 `room` + `compartment` 两字段，因为"主卧飘窗坐垫下"这种路径难以结构化
- 预置 12 项（7 房间 × 3 层位置），覆盖 80% 场景
- 用户可在设置页 CRUD，但**不开放 UI 给商品详情页**（详情页 <select> 仅选，管理来回跳转会破坏沉浸感）

#### item_templates（物品模版 — v2.0 新增）
| 字段 | 类型 | 说明 |
|------|------|------|
| tpl_id | INTEGER PK | |
| tpl_name | TEXT | 母婴待产包 / 粮油干货 / 应急药箱 / 旅行小药箱 |
| sort_order | INTEGER | 顺序 |
| is_active | INTEGER | 0/1（用户可禁用不看） |

#### template_items（模版-商品映射 — v2.0 新增）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | |
| tpl_id | INTEGER FK | |
| item_id | INTEGER FK |（创建时该商品可能不存在，允许 NULL 由前端按 tpl_item_key 决定） |
| tpl_item_key | TEXT | 模版内唯一键（如 `chanfu_diao`、`nk_60`），**核心字段** |
| base_qty | REAL | base 数量 |
| qty_mode | TEXT | per_adult / per_child / fixed / per_elder |
| est_days | REAL | 单件默认使用天数 |
| is_required | INTEGER | 是否强制（always show） |

**qty_mode 语义**：
| 值 | 含义 | 算法 |
|----|------|------|
| `fixed` | 永远 1 | qty = base_qty |
| `per_adult` | 与大人人数线性 | qty = base_qty × adults |
| `per_child` | 与小孩人数线性 | qty = base_qty × children |
| `per_elder` | 与老人数线性 | qty = base_qty × elders |
| `max_adult_child` | 两者最大值 | qty = base_qty × max(adults, children) |

**为什么用 tpl_item_key 而不是 item_id**：模版创建时，该商品尚未被用户实际录入，前端只是要"显示一个推荐行 + 等用户确认导入"。确认时按 tpl_item_key + 当前用户在批量页的 adjustment 创建真正的 items + inventory 行。

#### user_actions（审计线索 — v2.0 新增，MVP 可选）
| 字段 | 类型 |
|------|------|
| id | PK |
| action | capture_voice / capture_photo / capture_scan / manual_save / template_import / qty_adjust / mark_done |
| target_item_id | FK |
| payload | JSON |
| created_at | ISO |

**MVP 边界**：不上传云端，仅做本地 7 天滚动保留；用于 V2 估算法训练（哪类商品用户最常手动调整，说明估算法不准）。

### ER 更新
```
categories ──< items ──< item_specs
                   │
                   └──< inventory (1 active)
                   │
template_items >── items (可选，确认导入后绑定)

family_members（全局）
storage_locations（全局引用）
template_items >── item_templates

user_actions──> items（审计线索）
```

## 7. UI 规范（v2.0 原型终稿同步）

### 7.1 路由地图（screens ID）

| ID | 页 | 入口 | 关键 CTA |
|----|----|------|----------|
| s0 | 首页 | 默认已登录态 | 卡片进入 s1；4 入口卡片跳 s2/s3/s4/s5；模版卡跳 s6 |
| s1 | 商品详情（拖动调整） | 首页卡片、采购清单 | 滑杆调整 qty / 天数；保存/取消 |
| s2 | 拍照录入 | 首页"拍照录入"卡 | 拍照 → 识别 → 表单 → 入库 |
| s3 | 语音录入 | 首页"语音录入"卡 | 录音 → 解析 → 表单 → 入库 |
| s4 | 扫码录入 | 首页"扫码录入"卡 | 扫码 → 匹配/未中 → 表单 → 入库 |
| s5 | 手动录入 | 首页"手动录入"卡 / 扫码未命中 | 表单 → 入库 |
| s6 | 模版入口（选人 + 选模版） | 首页"模版导入"卡 / 底导"录入" | 步进器 → 选模版 → Go Btach |
| s7 | 我的 | 底导 | 统计、设置、反馈 |
| s8 | 批量调整（12 项竖排） | s6 → 进 | 顶步进器 → 单件破例 +/- → 确认导入 |

### 7.2 关键 UI 规则（v2.0 原型落地）

**首页卡片**：单张卡片 ≤ 78px 高，首屏 ≥ 3 张商品卡 + 模版主 CTA + 底栏（验证：iPhone SE 667px → firstCardTop=56px, bnBottom=667px OK）。

**详情页双拖动**：
- 拖动条 ≥ 44px 触控区
- 实时显示当前值：上方大字 + 拖动时变珊瑚色
- 天数滑杆与数量滑杆 **互不耦合**（用户常见误区：调整数量后应该天数不变；调整天数后数量不变）

**批量调整页**：
- 顶栏步进器 👴👨👶 按 `+` 后立刻脏写 `family_members` + 触发全表 `renderAdj()`；不等待用户点保存。
- 单项手动 +/- 独立于推荐值；用户一旦手动介入，该行 qty_mode 改为 `manual`，不再被步进器联动。
- `days` 自动按 `base_qty` + `est_days` 算；不随用户 +/- 调整。

**存储位置**：
- 详情页：单选下拉 + 一行"编辑位置"跳转入口
- 支持：房间=预置 9 项；位置=每房间 5 项（地面 / 柜内 / 抽屉 / 高处 / 堆叠）
- 用户自建：在"我的 → 设置 → 位置管理" CRUD，不支持商品详情页内删除（破坏沉浸感）

### 7.4 空态 vs 错误态（v2.0 新增）

| 状态 | 触发 | 文案 | CTA |
|------|------|------|-----|
| 空态-首页 | 首次使用，无清单 | "家里的宝贝，你说一句我就记住" | "🎤 语音录入第一件" |
| 空态-批量 | 选模版导入后模版为空 | "似乎选错了家庭人数" | "← 返回调整" |
| 错误-扫码 | 条码未命中 | "这个条码暂无数据，没关系，轻轻补一下就好" | "✍ 手动补一下" |
| 错误-网络 | 语音/拍照网络异常 | "识别暂不可用，可以用手动先记一记" | "✍ 手动录入" |
| 确认-标记用完 | 用户点"用完" | "确定用完？确定后将归档 7 天后从首页隐藏" | "确认用完 / 取消" |

## 8. 核心交互流程（UI 终稿对齐）

### 8.1 主路径：4 条入口等价入库
```
[首页 4 卡片] / [底导录入] → 4 路径之一
    │
    ├── 拍照录入：拍摄 → OCR 识别 → 用户确认 name/brand/specs → 填 qty/days/loc → 入库
    ├── 语音录入：录音 → 解析 "客厅白色柜子顶部的德宝纸巾还有5天，两包"
    ├── 扫码录入：扫 barcode → 匹配则跳转确认页 / 未匹配则跳手动
    └── 手动录入：选分类 → 填 4 步（基础/规格/库存/位置）→ 入库
         ↓ 任一成功后
[首页] 出现新卡片（色点：绿/黄/红）
```

### 8.2 辅助路径：模版批量导入（MVP 主推入口，降低冷启动成本）
```
[首页] → [模版导入 s6]
    → 步进器设置人数 (👴=0, 👨=2, 👶=0) → 保存到 family_members
    → 继续选择模版（按人数排序：独居→母婴→日用→药箱）
    → [批量调整 s8]
        → 顶步进器（同步 family_members）
        → 渲染 12 项（按 qty_mode × 当前人数）
        → 用户单项 +/- 破例
        → 确认导入
    → [首页] 12 张新卡片 + 新计数
```

### 8.3 单品修改路径
```
[首页卡片] → [详情 s1]
    → [拖动数量条] 或 [拖动天数条]
    → 保存 → 首页色卡实时更新
    → [标记用完] → 归档 → 首页移除
```

### 8.4 特殊场景：促销/活动日夜间采购
```
[首页] → [一键采购清单]
    → 滤出 remain_days < 7 的所有项
    → 生成文案（复制到微信 / 发给配偶 / 直接淘宝搜索）
    ↓ 用户下单后，跳回对应商品详情 → 改 qty
```

## 9. 估算法逻辑（保留 v1 设计，加误差分析）

### 9.1 核心公式

```
daily_usage = qty / est_days   (用户录入时给 est_days)
est_end_date = last_adjusted_at + remaining / daily_usage
remain_days = est_end_date - today
```

### 9.2 冷启动刷新流程

```javascript
// 小程序 onLaunch/onShow
const now = Date.now()
inventory.forEach(row => {
  const estEnds = row.last_adjust_at + (row.remaining / row.daily_usage)
  const remaining_days = (estEnds - now) / 86400000
  row.status = remaining_days <= 0 ? 'red'
              : remaining_days <= 3 ? 'yellow' : 'green'
  row.remain_days = remaining_days
})
// 发现黄色/红色 → 调 wx.requestSubscribeMessage
```

### 9.3 估算法误差来源 & 校准策略（v2 新增强调）

| 误差源 | 现象 | 处理 |
|--------|------|------|
| 初始 est_days 估计偏大（成人用纸：用户想 60 天，实际 20 天） | 早期"绿色过度"，用户不信任 | **MVP 策略**：每手动调 qty 一次写 actions 表，V2 用 5 次同类锚点反算 daily_usage |
| 开新包未及时录入 | 实物与数 1-2 包偏移 | **MVP 策略**：首页每张卡片置顶"+- 快调按钮"；减少操作摩擦 |
| 多人家庭用量不对称（老人用慢、孩子用快） | 不同房间消耗速率差异 | **MVP 策略**：暂不处理，等 V2 训练 per-user usage |
| 季节因素（夏季婴儿湿巾用量 ×2） | 月度级别波动 | **V2 特性** |

### 9.4 阈值定义

| 色 | 阈值 | 触发动作 |
|----|------|----------|
| 🔴 红 | remain_days <= 0 (已过期) or <= 1 (明后天用完) | 推送订阅消息 |
| 🟡 黄 | 1 < remain_days <= 3 | 首页醒目色块 + 可选推送 |
| 🟢 绿 | remain_days > 3 | 不干扰 |

**阈值来源**：电商标准配送 2-3 天 + 用户反应时间 1 天；化妆品预售 7-15 天需更早警示（预留 `presale_days` 字段，MVP 不设）。

### 15.2 风险

| ID | 风险 | 概率 | 影响 | 缓解 |
|----|------|------|------|------|

| R6 | 老人/保姆不信任数字型"7 天"，坚持实物查看 | 低 | 低 | 允许在备注字段写"实物看起来还剩很多" |
